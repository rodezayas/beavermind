## LLM output contract (JSON required from the model)

```json
{
  "one_thing": {"change": "...", "projected_score": 92},
  "brief": "...",
  "red_flags": ["..."],
  "dimensions": [
    {"dimension_id": 1, "score": 8, "band": "Strong", "reasoning": "quote-first...",
     "transcript_lines": ["[Dana]: ..."], "quick_fix": "...",
     "cap_fired": false},
    ...one entry per dimension...
  ]
}
```

`cap_fired` (optional, default false): the LLM evaluates the conditions of the
"Global Automatic Score Caps" table against the transcript; only then does the
engine trim to the cap maximum and note it in `reasoning`. Separation of
concerns: the condition is semantic (LLM), enforcing the maximum
is deterministic (code).

`grade` is not requested from the model: it is computed locally by summing scores and applying
the bands from the "Scoring Bands Reference" (R5) — that way the total is always
consistent with the dimensions and cannot be hallucinated.

## Decisions
- **The grade is computed in code, not generated by the LLM** (R5): it eliminates the
  entire class of hallucinations on the most visible datum of the report.
- **Caps applied in code** (R6): the LLM scores; the engine trims according to the
  caps table and notes in `reasoning` which cap fired. Deterministic and
  auditable.
- **`projected_score` bounded to `max_possible`** (R7): a "one thing" that
  promises more than possible is rejected as invalid.
- **Bands per dimension**: the Elite/Strong/Mid/Fail labels of the tables are
  accepted; any other label is rejected (R2).

## Alternative discarded
- Asking the LLM for the total and band directly: discarded because the total
  is deterministic arithmetic; delegating it to the model introduces errors that the
  coach sees first (and pdf_format.md requires the exact rubric band).
